# Implementation architecture

Foundation uses React 19.3.0, React DOM 19.3.0, TypeScript 7.0.2, Vite 8.3.4, Express 5.3.0 and tsx 4.23.15. Exact dependency resolutions are recorded in package-lock.json; `npm ci` reproduces them. Node.js 24.19.0 was used during foundation verification. Node 24+ is required for native `node:sqlite` DatabaseSync, avoiding a third-party native database build. The SQLite API remains runtime experimental where Node reports that warning.

Vite serves the development frontend and proxies `/api` to Express on port 3001. TypeScript checks frontend, backend and tests together. The API currently only exposes health; business routes follow subsequent issue specifications. SQLite is the shared server source of truth, not browser local storage. Prepared parameterized statements protect SQL values; foreign keys and CHECK constraints reject invalid rows. Transactions use BEGIN IMMEDIATE and rollback on failures. WAL supports reading while serialized writes occur. This synchronous embedded database is appropriate for a small university workload; a high-traffic hosted service would need a reviewed database/runtime design.

The schema separates users, tournaments, applications, player identities, persistent eligibility reservations, membership history, fixtures, goals and roster requests. Application player rows may be pending, while accepted eligibility will reserve a Student ID across the tournament. Membership history uses joined/removed timestamps; subsequent issues must enforce roster and historical scoring rules. Goals reference stable player identities with foreign keys. No application privacy route or role authorization is claimed by the foundation schema alone.

Environment configuration: PORT, DATABASE_PATH and future OAuth settings are listed in `.env.example`; real secrets are excluded by `.gitignore`. The schema is initialized idempotently on startup. Future structural schema changes require explicit migrations rather than relying on CREATE TABLE IF NOT EXISTS.

TT-01 verification: `npm test` passed one meaningful persistence/rollback test, and `npm run build` passed TypeScript checking and Vite production build. Independent QA still must review the issue before closure.

Registration interpretations (TT-04): Student IDs are trimmed and uppercased, with internal characters retained, and limited to 60 characters. Positions are Goalkeeper, Defender, Midfielder and Forward; shirt numbers are unique integers 1–99. One captain has at most one pending/accepted application per tournament. Pending applications cannot be edited; a rejected captain may submit a new application with a distinct team name. Accepted eligibility is reserved atomically and remains for the whole tournament. Pending/rejected applications do not reserve IDs. Contact accepts phone or email text; no format-specific assumption is imposed. Metadata columns are added idempotently on existing foundation databases.

Scheduling (TT-05): Single-round rotation algorithm inserts a bye for odd team counts. Generation is transactional, requires two accepted teams, and transitions registration to ongoing exactly once. Kickoff timestamps must include an explicit timezone and are persisted as UTC ISO strings; UI datetime fields use the viewer's local timezone and convert to UTC. No match duration or rest period was approved, so conflict prevention only rejects exact simultaneous kickoffs with the same team or same venue in the same tournament. Overlapping-duration and cross-tournament venue conflicts are not modeled. Schedule corrections remain allowed after results, preserving result history.

Results (TT-06): First valid result creates an immutable historical fixture roster using membership intervals at the scheduled kickoff. Joined timestamps must be at or before kickoff, and removed timestamps after kickoff. Unscheduled fixtures use first result-recording time as eligibility checkpoint. Future scheduled fixtures cannot be finalized. Later corrections use the snapshot, including removed players, and reject replacements who joined after that match. All goal events reconcile with score; own goals credit opposition without scorer totals. Derived standings use shared competition ranks and shared champions when complete.

Midseason (TT-07): Midpoint is interpreted as finished matches >= ceil(total/2), rather than an additional user-approved definition. Owner can open once while ongoing, then close; closed cannot reopen. Captains propose removals plus at most one replacement per removal; removal without replacement is allowed only when final roster stays 6–13 with a goalkeeper. Pending proposals leave the roster unchanged. Approval checks the active roster version and validates final roster atomically. Eligibility remains reserved permanently to a team; a previously removed player may return only to that same team. Membership intervals retain prior participation and snapshots preserve past results. A conflict or invalid final roster rolls back all changes.
